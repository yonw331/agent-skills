# 测试需求三层追问

把测试人员的价值前移：先问完整真实业务，再问清系统实现，最后决定风险由哪种测试方式承接。输出是可追溯的分析结果，不是测试用例，也不是对未确认内容的猜测。

## 工作流

### 1. 读取与定界

读取输入材料全文、项目上下文、目标路径规则和直接相关的术语、旧需求、原型或接口资料。识别输入类型：自然语言需求、PRD、开发设计、接口文档、流程图或已有测试需求。

先写出分析对象、来源、业务目标、范围、非目标和已知前置条件。若材料缺失或互相冲突，记录为待确认，不擅自选定。

完成标准：能够说明本次分析要帮助谁作出什么决定，并列出所有直接相关输入。

### 2. 第一层：业务落地追问

沿真实作业路径追问参与者、入口、参数、前置条件、主流程、实物变化、系统变化、外部系统变化、成功结果、异常分类、恢复方式、原流程兼容和范围边界。

对于每个动作回答：

- 谁在什么条件下做什么；
- 系统和外部设备分别做什么；
- 业务上如何判断成功；
- 失败后是忽略、暂停、取消、重试、恢复还是人工处理；
- 操作员下一步能做什么，不能做什么。

输出主流程、分支流程和业务问题清单。

### 3. 第二层：规格与架构追问

把业务动作映射到页面、接口、服务、数据、任务和状态。追问现有流程变化、复用边界、算法或规则、事务、并发、幂等、重试、补偿、外部状态映射和高风险设计点。

只在材料有依据时记录类名、字段名和协议名；业务结论优先使用业务语言，技术细节放入规格分析或附录。

输出规格映射、状态与数据影响、高风险点和需要产品/开发/外部系统确认的问题。

### 4. 第三层：测试方式追问

对每个风险明确承接方式：

- 功能手工测试：页面、角色、真实操作顺序、用户反馈和端到端可观察结果；
- 接口测试：参数、错误码、状态校验、幂等和跨服务契约；
- 单元测试：规则、算法、状态转换和边界计算；
- 端到端测试：跨模块、库存、任务、设备和业务闭环；
- 并发测试：竞态、重复提交、重复回调和唯一成功；
- 回归或自动化：稳定、重复、高频的既有链路。

记录测试数据、证据来源、无法执行的场景和后续自动化机会。不要因为用户说“功能手工测试”就把其他必要风险隐藏掉。

### 5. 输出与后续衔接

按 [references/output-template.md](references/output-template.md) 输出。问题生成参考 [references/question-catalog.md](references/question-catalog.md)，完成前执行 [references/quality-gates.md](references/quality-gates.md)。

若输入文档足够清楚且用户要求形成测试需求确认稿，可将本结果交给 `test-devdoc-to-requirements`；本技能不代替该技能编写 BR/AB/AC 正式确认稿。若仍有影响验收的待确认项，先暂停确认，不生成确定预期结果的正式用例。

## 事实状态

每个结论标记为：

- `已确认`：来源明确或用户已确认；
- `设计约束`：设计规定的实现边界；
- `待确认`：缺少会影响验收的事实；
- `推断`：有依据但未经确认，不能作为验收依据；
- `风险`：不澄清可能导致错误实现、遗漏覆盖或数据不一致；
- `不在范围`：仅在来源明确排除时使用。

缺少描述不能推断为“不支持”。保留原始文档，不覆盖需求、访谈、日志或测试记录。

## 输出完成标准

完成的输出必须同时具备：

1. 一句话业务目标和范围边界；
2. 业务落地层的主流程、异常和恢复问题；
3. 规格架构层的对象、状态、数据、接口和风险问题；
4. 测试方式层的风险到测试层级映射；
5. 已确认、待确认、推断和风险的清晰分离；
6. 可转化为测试需求确认或用例设计的追问结果；
7. 未确认项不被写成通过条件。
