# 开发文档转测试需求确认文档

把技术设计翻译成两层文档：先建立业务心智模型，再提供可测试、可追溯的需求。保留原设计文档，始终生成独立结果。

## 工作流

### 1. 读取上下文

1. 读取输入文档全文、Vault 根规则和目标目录最近的 `AGENTS.md`。
2. 若同目录存在原型、旧版 PRD、相关设计或术语资料，只读取与当前功能直接相关的材料。
3. 使用 `references/extraction-guide.md` 建立内部提取表，至少覆盖：业务目标、参与者、业务对象、术语、正常场景、分支、异常、实物变化、系统记录变化、状态、规则、数据、接口边界和非目标。

完成标准：源文档中每个业务章节都已映射到提取表，纯实现细节也已判断为“转译、附录保留或省略”之一。

### 2. 建立理解层

按 `assets/test-requirements-template.md` 先写理解层：

1. 用三到五句话说明问题、方案、使用时机和成功结果。
2. 列出参与者与业务对象，区分操作员、系统、设备和外部系统。
3. 在术语首次被后文依赖前，用白话解释术语；不要用另一个未解释术语作定义。
4. 先写一个具体示例，再写正常业务故事和场景差异。
5. 分开描述实物位置、业务任务、库存或数据记录的变化。

理解层描述业务流程步骤，不写页面点击手册。允许写“提交建单、系统分配、操作员确认、设备搬运”等业务动作；不写无助于理解的类名和调用链。

完成标准：不了解代码的测试人员只读理解层，即可回答“谁在什么条件下做什么、实物如何变化、系统如何变化、成功结果是什么、失败后怎么办”。

### 3. 建立测试确认层

1. 明确范围内、范围外和不受影响链路。
2. 将已确认行为写为连续编号的 `BR-01`、`BR-02`；每条包含条件、动作和结果，并保留来源。
3. 为有生命周期的业务对象写状态或阶段流转；没有独立状态机时写业务阶段，不发明状态。
4. 描述业务数据和可观察数据影响，避免用数据库字段代替业务含义。
5. 将异常和边界写为连续编号的 `AB-01`、`AB-02`，使用“如果……，则……”表达场景和预期。
6. 先写一条标为“端到端正常流程”的 AC，贯穿业务发起、核心处理、现实/任务/数据变化和成功结果；该 AC 必须验证功能确实完成，不能只验证请求格式、默认值或“不含某数据”。再为关键分支和高风险异常补充 AC。每条 AC 必须只有一个当前可判定的预期；一条 AC 的可观察结果可以包含同一成功场景下必须同时成立的多个结果。若完整结果尚未确认，只验收已确认的不变量，并把其余结果移入 🚧，不得写“按最终策略”“失败/处理中/待补偿均可”等开放结论。详细测试步骤留给后续 Spec 和测试用例。
7. 将缺失事实标记为 `🚧`，将有依据但未经确认的推断标记为 `📌`，分别汇总。
8. 将影响接口联调、数据验证、兼容性或发布门禁的技术证据放入附录；类名、字段名和协议名只在附录出现。
9. 区分观察时点。同一条件在候选展示、保存、提交、异步完成等阶段口径不同时，拆成多条规则，不用一条 BR 合并前端资格与后端最终校验。
10. 逐条确定追溯状态。包含任何未确认结果的 BR/AB 标为 🚧；不要把已确认原则和未确认结果按编号范围合并成“已确认”。
11. 约束动作边界。编辑、清除、撤销、重试等动作只适用于原文明示的对象阶段；不能从“清除待提交配置”扩展为“撤销已提交结果”。错误场景只写原文确认的阻断和副作用，不追加“保留旧值”等未说明承诺。
12. 不从缺失能力推导否定需求。原文只描述提交前动作时，只能确认提交前行为；“已提交后不支持撤销”仍是未知项，不得写成范围外或确定边界。

完成标准：BR、AB、AC 均唯一且连续；至少一条 AC 覆盖端到端正常流程，每条 AC 有唯一可判定结果；核心正常结果、关键分支、高风险阻断和不得绕过的既有校验均有 AC 直接关联；所有确认事实可追溯到原文；所有未确认内容已进入 🚧 或 📌 汇总，追溯状态与正文一致；追溯摘要保留逐条可核验的具体章节，不用宽泛章节范围代替精确映射。

### 4. 运行质量门禁

逐项执行 `references/quality-gates.md`。随后运行：

```bash
python3 <技能目录>/scripts/validate_requirements_doc.py <输出文件>
```

将 `<技能目录>` 解析为当前 `SKILL.md` 所在目录，不依赖技能安装在固定工作区路径。

验证失败时修正文档并重跑，不得把失败项留给用户自行发现。脚本通过不等于内容通过，仍需执行理解性人工门禁。

### 5. 归档并暂停确认

- 输出位置：`{项目目录}/设计文档/test-req-{功能名}.md`
- Frontmatter 使用 Vault 合法状态 `status: ongoing`，另用 `review_status: draft` 表示待评审；保留模板自动提供的 `document_schema: tdtr/v1`，用于机器识别文档契约版本。
- 不覆盖原设计、旧 PRD、访谈、日志或人工记录。

输出待确认项和推断项后暂停，不继续拆 Spec 或生成测试用例。用户反馈后按以下规则更新：

| 反馈 | 处理 |
| --- | --- |
| 🚧 已确认 | 写入确认事实，删除该处 🚧 |
| 🚧 暂不处理 | 标为“已确认暂不处理”，并明确影响 |
| 📌 正确 | 保留内容，删除 📌 |
| 📌 有误 | 按反馈修正，删除 📌 |
| 新信息 | 写入对应层；仍未确认则新增 🚧 |

所有 🚧/📌 闭环且用户明确同意定稿后，将 `review_status` 改为 `reviewed`，追加 `reviewed` 日期和 `reviewer`。`status` 继续遵守 Vault 的项目状态语义。

## 约束

- 使用业务语言解释实现结果，不把技术标识符简单删除后留下语义空洞。
- 不将开发方案中的设计建议自动当成已确认需求；根据措辞和上下文标为事实、约束、🚧或📌。
- 不机械添加用户故事、KPI、埋点、性能、安全或权限要求；源文档有依据或当前功能必需但缺失时才记录。
- 不把接口和数据结构全部丢弃；对测试有价值的技术契约进入附录。
- 不调用 `test-prd-splitter`、`test-case-generator` 或 `tester-pipeline`，除非用户另行明确要求。
