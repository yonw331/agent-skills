# 提取与转译指南

## 提取顺序

先按读者理解顺序提取，而不是按原文代码章节顺序复制：

1. 为什么做、解决谁的什么问题。
2. 谁或什么参与：人员、系统、设备、单据、容器、库存等。
3. 正常情况下从哪里开始、经过什么、到哪里结束。
4. 不同场景为什么分流。
5. 实物、任务和系统数据分别如何变化。
6. 哪些条件允许或阻止动作。
7. 异常如何恢复，失败后什么事实必须保留。
8. 范围外和保持不变的行为。

## 证据分类

| 原文内容 | 转换目标 |
| --- | --- |
| 背景、目的、业务口径 | 问题、目标、范围、正常业务故事 |
| 页面、角色、操作描述 | 参与者、业务动作、可观察结果 |
| 调用链、处理器、服务 | 系统在该阶段产生的业务结果；类名只在附录保留 |
| 状态枚举、流程图 | 中文阶段/状态及合法转换 |
| 表结构、字段 | 业务对象和数据变化；字段名只在附录保留 |
| 接口、消息、外部回调 | 系统边界、触发、输入输出和失败契约 |
| 并发、锁、幂等 | 用户可观察的重复提交、冲突、回滚和一致性规则 |
| 发布、回滚、前置修复 | 发布门禁、依赖、兼容性和回归范围 |
| “建议、如接入、评估后、后续” | 不自动视为已确认；标为 🚧 或范围外候选 |

## 三条变化线

复杂仓储、物流、支付或审批流程必须分别追踪：

- **实物或现场线**：对象实际在哪里、谁移动或操作它。
- **任务线**：业务单、作业任务、调度任务处于什么阶段。
- **数据线**：系统记录、库存、余额、状态或关联关系如何变化。

三条线不适用时，改成与领域匹配的三条线，但必须把现实世界动作与系统记录分开。

## 术语落地

- 术语首次出现时解释业务概念，不只展开缩写。
- 优先使用一个具体例子解释抽象关系。
- 同义词选一个作为主术语，其他词只在“容易混淆”中说明。
- 若原文术语本身冲突或含义漂移，记录 🚧，不要擅自统一。

## 事实、缺口与推断

| 类型 | 判定 | 写法 |
| --- | --- | --- |
| 已确认事实 | 原文明示且无冲突 | 正文规则，标原文章节 |
| 技术约束 | 原文明示且影响可测行为 | 业务化写正文，技术证据写附录 |
| 信息缺口 | 原文缺失、矛盾或只给方向 | 🚧，写成会改变范围或预期的问题 |
| 合理推断 | 可由多个事实支持但未明示 | 📌，同时写推断依据 |
| 无关实现 | 不影响功能理解、测试或发布 | 省略 |

不要把所有可能问题都列成缺口。只有不同答案会改变范围、流程、状态、数据、接口契约或测试预期时，才进入待确认事项。

### 确认状态隔离

- 原文同时写了确定目标和“建议、需要确认、技术可行时、若不能”时，只把稳定不变量写成已确认事实。
- 未确定的终态、回滚、补偿、响应或任务类型进入 🚧，不得借“原则已确认”包装成可执行结果。
- 一条规则混有已确认与未确认部分时必须拆开；含未确认结果的规则来源标 🚧。
- 追溯摘要逐条或按同一确认状态分组；任何范围内存在 🚧/📌 时，该组不能标“已确认”。

### 观察时点

页面候选、录入、保存、提交、异步完成是不同观察时点。原文只要求提交时校验的条件，不得提前写成页面禁用或候选过滤；反之亦然。一个 BR 只描述一个观察时点，跨时点行为拆成多条规则。

编辑、清除、撤销和重试也受观察时点约束。原文描述提交前清除配置时，只能写“清除尚未提交的配置”；已提交结果能否撤销属于另一个能力，缺失时记录 🚧。原文只写“禁止保存”时，不推断旧值保留、草稿清空或页面回退。

“原文没有描述”不等于“不支持”。缺少已提交结果撤销、跨单操作或某种入口说明时，不能直接放入范围外、不受影响或确定规则；若不同答案改变业务范围，记录 🚧。

## 业务规则写法

每条 BR 保持原子性，并尽量包含：

```text
当/如果 <条件>，<角色或系统> 执行 <动作>，结果为 <可观察结果>。
```

避免：

- 只写实现动作：“调用某服务更新某字段”。
- 只写口号：“保证数据一致性”。
- 一条规则同时包含多个可独立变化的条件分支。
- 把“尚待确认、需评估、后续决定”本身写成 BR/AB；纯缺口只进入待确认事项。若存在稳定不变量，拆出不变量作为 BR/AB，未确认结果单独进入 🚧。

## 核心验收点选择

按以下顺序选择：

1. 一个标为“端到端正常流程”的场景，贯穿触发、核心处理、现实/任务/数据变化和成功结果。不能用多个零散 AC 代替，也不能只验证默认值、请求字段或“不发生某事”。
2. 每个会产生不同业务结果的关键分支。
3. 数据丢失、重复处理、跨范围写入或无法恢复的高风险异常。
4. 新入口必须复用且不得绕过的既有权限、状态、库存或业务校验；至少用一条核心 AC 证明兼容门禁仍生效。

AC 写前提、动作和可观察结果，但不展开为逐点击测试步骤。每个 AC 关联至少一个 BR 或 AB。

写完后从业务目标反查：正常模式是否证明业务真正完成，关键阻断是否证明没有产生错误副作用。追溯摘要只能引用真实关联的 AC，不能用 AC 编号区间制造覆盖假象。

追溯摘要的来源精度不低于正文。多条规则来源不同就拆行，不以“原设计 1～9”之类宽泛范围代替逐条证据。

AC 必须可二值判定。完整失败契约尚未确认时，只写已确认的不变量，例如“不得展示完全成功”“不得消费历史库存”；回滚、保留、处理中或待补偿等互斥结果进入 🚧，确认后再新增或改写 AC。
