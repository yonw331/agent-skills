# 输出质量门禁

## 1. 理解性

- 一页读懂部分说明问题、方案、时机和成功结果。
- 参与者与业务对象没有混为一谈。
- 术语在首次依赖前已解释。
- 至少有一个具体示例贯穿正常流程。
- 正常流程先于异常、数据表和实现约束。
- 读者能区分人员、系统、设备和外部系统的动作。
- 现实世界变化与系统记录变化分开描述。

失败信号：读者必须追问“这个对象到底有没有移动”“这个词是什么意思”“谁执行这个动作”“为什么需要返回”等核心问题。

## 2. 可测试性

- 每条 BR 有条件、动作和结果，不只描述技术实现。
- 纯待确认陈述只在待确认事项中，不占用 BR/AB 编号。
- 每条 AB 有明确场景和可观察预期。
- AC 覆盖正常、关键分支和高风险异常，不与详细测试用例重复。
- 至少一条 AC 明确标为“端到端正常流程”，并证明业务成功及关键现实/任务/数据结果；零散字段或局部动作不能替代。
- 普通/兼容路径不仅验证“不带新增信息”，也验证原业务结果确实成功。
- 每条 AC 只有一个当前可判定的预期，不依赖“最终确认”“按策略处理”或多个互斥结果任选其一。
- 状态转换有触发条件，终态和阻断条件可识别。
- 数据变化使用业务含义，并说明发生时点。
- 页面候选、保存、提交和异步完成的校验时点没有混写。
- 编辑、清除、撤销、重试没有跨越原文未授权的对象阶段，异常结果没有附加无来源的旧值保留承诺。
- 没有把原文未描述的能力直接写成“不支持”或范围外；影响范围的未知能力进入 🚧。
- 新入口声称复用的既有关键校验至少有一个核心 AC 证明未被绕过。
- “正常、合理、支持、适当、完整、友好”等模糊词已量化、解释或标 🚧。

## 3. 追溯性

- 已确认规则标注原文章节。
- BR、AB、AC 编号唯一且连续。
- AC 关联有效的 BR 或 AB。
- 追溯摘要只列真实 AC 关联，不用编号区间暗示未覆盖规则已有验收点。
- 追溯摘要来源与正文同样具体，不用宽泛章节范围掩盖多条规则的不同证据。
- 所有 🚧 都出现在待确认事项中。
- 所有 📌 都出现在推断项中。
- 追溯摘要没有把含 🚧/📌 的编号范围标为“已确认”。
- 技术附录中的证据说明测试价值，不堆放完整代码调用链。

## 4. 下游兼容

- 包含功能目标、范围、非目标、BR、状态或阶段流转、数据影响、AB 和待确认项。
- 规则与异常保持稳定编号，后续 Spec 可直接引用。
- 文档不提前生成完整测试用例，不与 `test-case-generator` 职责重叠。
- 未闭环 🚧/📌 时明确暂停，不进入 Spec 拆分。

## 5. Vault 与安全

- 原设计和人工记录未被修改或覆盖。
- 输出为独立 `test-req-*` 文件。
- Frontmatter `status` 使用 Vault 合法值，评审状态单独记录。
- Frontmatter 保留 `document_schema: tdtr/v1`，用于自动识别文档契约版本。
- 不写入密钥、令牌、个人敏感信息或生产数据。
- 技术证据不包含无必要的内部绝对路径、完整凭据或敏感日志。
